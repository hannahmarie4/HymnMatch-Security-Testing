Security Implementation Report

HymnMatch: AI-Powered Hymn Recommendation System

Prepared for: IT Security & Software Engineering
Date: May 24, 2026

Section 1: Introduction

1.1 System Overview

HymnMatch is a web-based application designed for choir directors to upload liturgical documents—such as Mass readings and parish bulletins—and receive AI-powered hymn recommendations that match the themes and liturgical season of each service. The system leverages Optical Character Recognition (OCR) to extract text from uploaded documents and uses the Google Gemini API to analyze themes and suggest appropriate hymns from a curated database.

1.2 Technology Stack

  • Frontend: React (Vite), hosted on Vercel
  • Backend: Node.js / Express, hosted on Render
  • Database & Authentication: Supabase (PostgreSQL with built-in Auth)
  • AI Engine: Google Gemini 1.5 Flash API
  • OCR: Google Cloud Vision API

1.3 Currently Implemented & Testable Features

  • Sign Up with client-side input validation (name, email, password)
  • Sign In with bcrypt password hashing via Supabase Auth
  • Forgot Password / Reset Password flow with email verification
  • Password visibility toggle on all password fields
  • Terms & Conditions acceptance modal
  • Generic error messages that do not expose system internals
  • Supabase-managed authentication and session handling

1.4 Purpose of This Report

This report identifies the key security threats facing HymnMatch, documents the security controls implemented to mitigate each threat, maps every control to the CIA Triad (Confidentiality, Integrity, Availability), and provides working code snippets that demonstrate each implementation. The goal is to show that security was treated as a foundational requirement—not an afterthought—throughout the development of the application.

Section 2: Threat & Vulnerability Identification

The following table summarizes the six primary threats identified during the security analysis of HymnMatch. Each threat is paired with the specific vulnerability it exploits and the potential impact on the system and its users.

Threat Possible Vulnerability Impact
1. Unauthorized Access to User Accounts Weak password authentication mechanisms that allow simple or commonly-used passwords Attacker gains access to saved songs, personal settings, and liturgical preferences associated with the compromised account
2. SQL Injection / Database Attacks Absence of input validation on user-supplied inputs, allowing malicious SQL to be injected into queries Full database compromise, theft or corruption of user data, unauthorized read/write access to all records
3. Data Leakage of Uploaded Documents Permanent storage of uploaded liturgical documents without encryption or proper access controls Sensitive liturgical materials, parish schedules, and internal church documents exposed to unauthorized parties
4. Brute Force / Weak Password Attacks No rate limiting on login attempts, allowing unlimited authentication requests Automated tools systematically guess passwords, leading to mass account compromise across the platform
5. Cross-Site Scripting (XSS) Unsanitized text inputs rendered directly in the DOM without escaping or encoding Attacker injects malicious scripts to steal session tokens, hijack accounts, or redirect users to phishing sites
6. API Key Exposure API keys stored in frontend JavaScript bundles or transmitted without encryption Unauthorized use of the Gemini API resulting in budget drain, quota exhaustion, and potential service disruption

Section 3: Security Controls Implementation

For each threat identified in Section 2, a corresponding security control has been designed and implemented. This section documents the control name, the threat it addresses, the CIA principle it upholds, a description of its implementation, and the relevant code.

Control #1: Password Hashing

  • Threat Addressed: Unauthorized Access to User Accounts
  • CIA Principle: Confidentiality
  • Implementation Description: Passwords are hashed using the bcrypt algorithm before being stored in the database. Supabase Auth automatically handles password hashing during the sign-up and password-reset flows. At no point is a plain-text password written to persistent storage. Even if the database is compromised, attackers cannot reverse the bcrypt hash to obtain the original password. The cost factor used by Supabase's bcrypt implementation makes brute-force reversal computationally infeasible.

Code Snippet:

const signUpUser = async (email, password, fullName) => {
  const { data, error } = await supabase.auth.signUp({
    email: email,
    password: password
  });
  // Supabase hashes password using bcrypt automatically
  // Plain-text password is NEVER stored in the database
  return data;
};

Control #2: Input Validation & Prepared Statements

  • Threat Addressed: SQL Injection / Database Attacks
  • CIA Principle: Integrity
  • Implementation Description: All user inputs are validated on the client side before submission. The name field accepts only letters and spaces (regex-enforced). The email field must match a standard email format. Passwords must be at least 8 characters and include letters, numbers, and at least one special character. On the server side, Supabase uses parameterized queries internally, which prevent SQL injection by separating SQL logic from user-supplied data.

Code Snippet:

const validateInput = (name, email, password) => {
  const nameRegex = /^[A-Za-z\s]+$/;
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  const passwordRegex =
    /^(?=.*[A-Za-z])(?=.*\d)(?=.*[@$!%*#?&])[A-Za-z\d@$!%*#?&]{8,}$/;

  if (!nameRegex.test(name))
    return "Name must contain letters only";
  if (!emailRegex.test(email))
    return "Invalid email format";
  if (!passwordRegex.test(password))
    return "Password must be 8+ chars with letters, numbers, special character";

  return "Valid";
};

Control #3: Row Level Security (RLS)

  • Threat Addressed: Data Leakage of Uploaded Documents
  • CIA Principle: Confidentiality & Integrity
  • Implementation Description: Supabase Row Level Security (RLS) is enabled at the PostgreSQL database level. RLS policies ensure that every query is automatically filtered by the authenticated user's ID. Users can only view, insert, update, or delete their own saved songs and audit log entries. Even if a malicious user crafts a direct API request, the database enforces access boundaries, preventing cross-user data access.

Code Snippet:

-- Enable Row Level Security on the saved_songs table
ALTER TABLE saved_songs ENABLE ROW LEVEL SECURITY;

-- Policy: Users can only SELECT their own saved songs
CREATE POLICY "Users can view own saved songs"
ON saved_songs FOR SELECT
USING (auth.uid() = user_id);

-- Policy: Users can only INSERT their own saved songs
CREATE POLICY "Users can insert own saved songs"
ON saved_songs FOR INSERT
WITH CHECK (auth.uid() = user_id);

Control #4: Session Management & Rate Limiting

  • Threat Addressed: Brute Force / Weak Password Attacks
  • CIA Principle: Integrity & Availability
  • Implementation Description: Supabase Auth manages secure JWT-based sessions with automatic expiration and refresh-token rotation. Login endpoints are protected by built-in rate limiting that restricts the number of authentication attempts from a single IP address within a time window. After multiple consecutive failed login attempts, the system temporarily locks the account and returns a rate-limit error. The application handles this gracefully by displaying a user-friendly message without revealing system internals.

Code Snippet:

const handleLogin = async (email, password) => {
  const { data, error } = await supabase.auth
    .signInWithPassword({
      email: email,
      password: password
    });

  if (error && error.message.includes('rate limit')) {
    return "Too many login attempts. Please try again later.";
  }

  // Generic error message — no system details exposed
  if (error) {
    return "Invalid email or password.";
  }

  return data;
};

Control #5: Input Sanitization & XSS Prevention

  • Threat Addressed: Cross-Site Scripting (XSS)
  • CIA Principle: Integrity
  • Implementation Description: All user-generated content is sanitized before being rendered in the DOM. React's JSX rendering engine automatically escapes interpolated values, which prevents inline script injection by default. Any value placed inside curly braces in JSX is treated as a text node, not executable HTML. For cases where raw HTML must be rendered, a custom sanitization function escapes dangerous characters. The application never uses dangerouslySetInnerHTML with unsanitized input.

Code Snippet:

// React automatically escapes text content in JSX
const DisplayUserName = ({ unsafeInput }) => {
  return <h1>{unsafeInput}</h1>;
  // React escapes unsafeInput, preventing XSS
};

// Custom sanitization utility for additional protection
const sanitizeInput = (input) => {
  const div = document.createElement('div');
  div.textContent = input; // textContent escapes HTML entities
  return div.innerHTML;
};

Control #6: Secure API Key Management

  • Threat Addressed: API Key Exposure
  • CIA Principle: Confidentiality
  • Implementation Description: The Google Gemini API key is stored exclusively in the backend server's .env file and is loaded at runtime using the dotenv library. The key is never included in frontend source code, never committed to version control, and never transmitted to the client. The Node.js/Express backend acts as a secure proxy: the frontend sends extracted text to the backend, which authenticates with the Gemini API on the server side and returns only the processed recommendation. Error responses use generic messages to avoid leaking system configuration details.

Code Snippet:

require('dotenv').config();
const { GoogleGenerativeAI } = require('@google/generative-ai');

// API key loaded from .env — never exposed to frontend
const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY);

app.post('/api/analyze-reading', async (req, res) => {
  try {
    const { extractedText } = req.body;

    // Backend makes the request securely
    const model = genAI.getGenerativeModel({
      model: "gemini-1.5-flash"
    });

    const result = await model.generateContent(extractedText);

    // Send result to frontend — API key NEVER exposed
    res.json({ recommendation: result.response.text() });
  } catch (error) {
    // Generic error message — no system details leaked
    res.status(500).json({ error: "Processing failed" });
  }
});

Section 4: CIA Triad Application

The CIA Triad—Confidentiality, Integrity, and Availability—serves as the foundational framework guiding every security decision in HymnMatch. This section maps how the implemented controls collectively satisfy each principle.

4.1 Confidentiality

Confidentiality ensures that sensitive information is accessible only to authorized individuals. In HymnMatch, confidentiality is enforced through multiple layers:

  • Password Hashing (Control #1): User passwords are hashed using bcrypt before storage. Even in the event of a database breach, the original passwords remain computationally infeasible to recover.
  • Row Level Security (Control #3): RLS policies at the PostgreSQL level ensure that users can only query and modify their own data. Cross-user data access is blocked at the database engine level, not merely at the application layer.
  • Secure API Key Management (Control #6): The Gemini API key resides exclusively in the backend server's environment variables. It is never bundled into frontend JavaScript, never appears in browser network requests, and is excluded from version control via .gitignore.
  • Temporary Document Processing: Uploaded liturgical documents are processed in temporary browser memory during OCR extraction and are not permanently stored on servers, minimizing the window of exposure.

Together, these controls ensure that all sensitive information—passwords, user data, API credentials, and uploaded documents—is protected from unauthorized disclosure at every stage of the data lifecycle.

4.2 Integrity

Integrity ensures that data remains accurate, consistent, and unaltered by unauthorized parties. HymnMatch enforces integrity through:

  • Input Validation & Prepared Statements (Control #2): Client-side regex validation and server-side parameterized queries work together to prevent SQL injection. Malicious input cannot alter the structure of database queries, preserving data accuracy.
  • Session Management & Rate Limiting (Control #4): Rate limiting prevents brute-force attacks from systematically guessing passwords. By restricting the volume of authentication attempts, the system preserves the integrity of user credentials and prevents unauthorized account modifications.
  • Input Sanitization & XSS Prevention (Control #5): React's automatic escaping and custom sanitization utilities prevent attackers from injecting malicious scripts that could alter page content, steal session tokens, or modify data displayed to other users.

These controls collectively guarantee that data flowing into, through, and out of HymnMatch remains trustworthy and uncompromised.

4.3 Availability

Availability ensures that the system and its data remain accessible to authorized users when needed. HymnMatch ensures availability through:

  • Cloud Infrastructure: The frontend is hosted on Vercel and the backend on Supabase and Render—enterprise-grade platforms that provide automatic scaling, redundancy, and uptime guarantees. Supabase manages automated database backups to prevent data loss.
  • Graceful Error Handling: If the Gemini API experiences downtime or returns an error, the application displays a user-friendly message ("Processing failed") rather than crashing or exposing a stack trace. Users can continue using other features while the AI service recovers.
  • Session Continuity: Supabase Auth's JWT-based sessions with automatic refresh-token rotation ensure that users remain authenticated across browser sessions and system updates, preventing unnecessary disruptions to their workflow.
  • Rate Limiting Protection: By throttling excessive login attempts, rate limiting also protects availability by preventing denial-of-service conditions caused by authentication endpoint abuse.

Section 6: Conclusion

Developing HymnMatch has demonstrated that security must be planned before development begins, not added as an afterthought. By identifying threats early in the design phase and implementing corresponding security controls from the start, the system inherently resists compromise and provides users with confidence that their church data is protected.

The six security controls documented in this report address the most critical threat vectors facing the application: unauthorized access, injection attacks, data leakage, brute-force attacks, cross-site scripting, and API key exposure. Each control is mapped to one or more principles of the CIA Triad, ensuring comprehensive coverage of confidentiality, integrity, and availability.

Key takeaways from this security implementation include:

  • Defense in Depth: No single control is relied upon in isolation. Multiple overlapping layers—client-side validation, server-side parameterization, database-level RLS, and infrastructure-level rate limiting—work together to create a robust security posture.
  • Principle of Least Privilege: Row Level Security ensures that every database query is scoped to the authenticated user. Users never have access to data beyond their own scope.
  • Secure by Default: Technologies were chosen specifically for their built-in security features. React prevents XSS by default, Supabase handles bcrypt hashing automatically, and parameterized queries eliminate SQL injection without additional developer effort.
  • Minimal Exposure: Sensitive assets—API keys, passwords, uploaded documents—are either encrypted, hashed, proxied through the backend, or processed ephemerally to minimize the attack surface.

Security is not a feature—it is a foundational principle that must be woven into every layer of the application. HymnMatch's architecture reflects this philosophy, ensuring that choir directors can trust the platform with their liturgical data and focus on what matters most: selecting the right hymns for their congregation.
